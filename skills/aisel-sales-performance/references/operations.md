# 운영 절차

## 먼저 확인할 상태

프로젝트 `docs/sales-performance.json`을 읽고 실제 환경과 대조한다. UI 배포, 데이터 접근 보호, 백엔드 준비, 예약 러너 배포, 첫 게시 검증은 별개다. 최신 성공 집계가 없으면 기다리는 화면을 유지한다. 2026-10-07 v2 권한은 Firebase Console에서 기존 전체 규칙을 읽고 판매성과 노드만 수정·게시한 뒤 새로고침한 전체 JSON 일치를 확인했다. 이 확인을 새 v2 실데이터 게시 완료로 확대하지 않는다.

기존 GitHub Pages 작업지시서와 승인된 Site 호스팅을 유지한다. Site 호스팅의 현재 공개 상태는 유지하되 판매 집계 API는 인증으로 보호한다. 다른 호스팅으로 이전하거나 공개 집계 API로 바꾸지 않는다. Site의 작업 API는 접근 토큰과 별도 서비스 인증으로 보호한다.

## 인증 경계

- 판매 화면은 기존 Firebase 설정을 재사용한 이름 있는 앱 `aiselSalesReadOnly`로 인증과 데이터 연결을 분리한다. 기본 앱 로그인으로 대체하면 기존 시트 반영 콜백이 작지·사진을 갱신할 수 있다.
- 승인된 소유자 Google 계정은 `current`와 일별 `daily/<period.end>` 집계를 읽고, `products/<품번>`의 확인된 분류·출시일·핵심 SKU 후보를 기록하며 `reviews/<품번>/<기록ID>`에 판단을 추가한다. 집계 전용 계정은 `current`와 `daily`만 읽기·갱신하며 상품 기준·사람의 판단은 쓰지 않는다. 실제 권한 판정은 Firebase 규칙에서 수행하고 배포 전후를 JSON에서 구분한다.
- 비로그인·권한 없는 요청, 요약 삭제, 루트 읽기를 허용하지 않는다. 기존 작업지시서 경로의 동작을 별도로 검증한다.
- 집계 계정 발급에 사용한 임시 익명 로그인 제공업체는 현재 꺼져 있다. 기존 전용 계정을 재사용하며, 자동 재발급이나 제공업체 재활성화로 복구하지 않는다.
- 로그아웃·계정 변경 때 화면 캐시와 펼친 내용을 비우고 이전 인증 세대의 진행 중 응답을 버린다. 인증 실패를 판매 0으로 표시하지 않는다.

## 집계·게시 계약

2026-10-06 승인 기준은 최근 7일 비교와 날짜별 집계·주간 판단 기록이다. schema v2·이력·상품 메타/리뷰 경로의 구현과 권한 배포는 프로젝트 JSON `productPerformanceChange20261006`에서 실제 검증 상태를 확인한다. 기록 권한은 문서가 아닌 실제 배포 규칙과 재조회로 확인한다.

기본 주기는 매일 오전 6시 한국 시간이다. 서버가 한국 날짜를 계산하고 어제까지 최근 7일·직전 7일·최근 28일을 구분해 집계한다. 러너는 결과의 기간 검증을 위해 실행 시작 시 한국 날짜를 내부 `runDate`로 고정하지만 이 값을 API에 보내지 않는다. 자정을 지나 완료돼도 시작 시 고정한 날짜의 집계 기간과 일치하면 검증할 수 있다. 반환된 기간이 그 기준과 다르면 게시하지 않는다. 예약 지연은 허용하되 마지막 성공 시각을 표시한다.

준비된 러너는 다음 흐름을 사용한다.

1. `POST /api/workorder-sales/jobs`의 JSON 본문은 정확히 빈 객체 `{}`로 보낸다. `runDate` 등 추가 키를 넣지 않는다. 서버가 집계 날짜를 계산하며 같은 날짜 작업은 재사용한다. 과거 실행에서 `runDate`를 보낸 시작 요청은 HTTP 400으로 거절되었다.
2. 작업 ID와 증가하는 revision을 확인하며 제한된 횟수로 다음 묶음 수집을 진행한다.
3. `ready`, `coverage.complete: true`, 결과 준비를 모두 확인한 뒤 요약 결과를 받는다.
4. 새 게시에는 v2만 허용하고 기존 v1은 읽기 호환으로 유지한다. 최근 7일·직전 7일·28일 기간과 날짜순 일별 28개, 상품별 허용 필드를 검증한다. Firebase가 제거하는 명시적 null은 읽기 검증에서 복원하되 증거 없는 수량을 0으로 바꾸지 않는다. 원주문·고객정보·원본사진을 요약이나 로그에 넣지 않는다.
5. 전용 Firebase 계정으로 현재 요약과 ETag를 읽는다. 과거 결과로 덮어쓰지 않고 동일 결과도 다시 저장하지 않는다.
6. v2는 먼저 `daily/<period.end>` 이력을 `If-Match`로 저장·재조회한 뒤 `current` 요약을 같은 방식으로 게시·검증한다. 이력이 실패하면 현재 요약을 보존한다. 이력에는 기간 스냅샷과 일별 집계만 넣고 원주문·고객정보는 넣지 않는다. 두 경로의 실제 검증까지 끝나야 성공이다.

`coverage.complete: true`는 필요한 원천 페이지를 모두 열거했다는 뜻이다. 모든 상품의 취소·교환 수량까지 확정됐다는 뜻은 아니다. 원천 열거가 끝난 정상 요약에도 상품별 미확정 지표가 포함될 수 있으며, 이때 서버가 `netQty`, `rank`, `gauge`를 `null`, 평가를 `pending`으로 둔 상태를 허용한다. 확인된 다른 상품의 수량은 유지한다.

검증 전 실패는 마지막 정상 집계를 유지한다. ETag 충돌·불명확한 POST/PUT 결과를 반복 실행하지 않는다. PUT 이후 재조회 실패는 이미 저장됐을 수 있으므로 실패 상태를 보고 실제 값을 확인한다. 다른 실행의 결과를 덮는 자동 되돌리기는 하지 않는다.

러너 시간 제한에 도달해도 서버 작업이 `running`이고 체크포인트가 남아 있다면 수집 전체가 사라진 것은 아니다. 상태를 확인한 뒤 다음 같은 한국 날짜 실행에서 `POST /api/workorder-sales/jobs`에 `{}`를 보내 기존 작업을 이어받는다. 수집 진행이 남아 있는 상황에서 소유자 초기화·재시작 버튼부터 누르지 않는다. 이 절차는 확인된 서버 체크포인트의 다음 실행 재개이며, 응답이 불명확한 쓰기 요청을 즉시 반복하는 것과 구분한다.

이미 `ready`인 같은 날짜 작업은 새 실행에서도 이전 결과를 재사용할 수 있다. 수집기 코드를 보완한 뒤 그날 예약에 수정본을 적용해야 하면, 승인된 소유자 경로로 기존 게시 요약을 보존한 재검증을 한 번 준비하고 `queued` 상태·단계·revision을 확인한다. 준비 자체로 자동 진행이나 즉시 워크플로 실행을 붙이지 않고 설정된 예약을 기다린다. 완료된 실행·마지막 성공 기록은 그대로 두고 다음 예약 재검증 상태를 별도 기록한다. 이 절차를 진행 중 체크포인트의 재개와 혼동하거나 같은 준비를 반복하지 않는다.

토큰은 서버 비밀값 저장소에서만 취급한다. 원문 인증정보, 계정 UID, 응답 본문을 코드·문서·로그·GitHub·ZIP·Drive에 포함하지 않는다. 다른 출처로 리다이렉트하거나 응답이 제공한 임의 URL에 인증 헤더를 전달하지 않는다.

## 순위와 화면 검증

상품 연결은 프로젝트의 `docs/product-mapping.json`에 기록된 근거를 사용한다. 품번으로 직접 연결되지 않으면 공백만 정규화한 전체 상품명이 카페24 전체 목록에서 유일하게 일치하는지 확인한다. 부분 일치·유사도·일괄 접미어 제거로 연결하지 않는다.

2026-10-03 확인된 연결은 정확한 유일 상품명 일치 9개와 사용자가 직접 확인한 별칭 1개, 총 10개다. 별칭은 `AS-26F-KT-021`의 ‘밀로 라인 랩 니트’와 카페24 `product_no 1170`의 ‘밀로 라인 랩 니트 탑’ 한 쌍만 허용한다. 모든 상품에서 ‘탑’을 제거하는 규칙으로 확장하지 않는다.

`AS-26F-CP-002` 스트레이트 팬츠의 참고 링크가 가리킨 `product_no 951`은 부츠컷 제품이므로 연결하지 않는다. 레퍼런스 링크나 비슷한 품명이 같은 판매 상품임을 보장하지 않는다. 현재 연결 근거 확정과 수집기의 실제 배포·집계 성공은 별개이며 최신 상태 JSON으로 구분한다.

알려진 순판매수량을 내림차순으로 정렬한다. 신뢰할 수 있는 순매출이 있을 때 동률 비교에 사용한다. 매출 비교가 불가능한 공동 순위 여부는 서버 결과를 유지한다. 화면은 순위를 새로 추측하지 않는다.

`netQty: 0`, `netQty: null`, 상품 연결 실패를 구분한다. `netRevenue: null`이어도 확인된 실제 수량과 서버가 제공한 순위·게이지는 유지한다. `coverage.complete: false`면 순위·게이지·평가를 보류한다. 원천 페이지 열거가 완료된 경우, 수량 미확정 상품의 순위는 보류하면서 확인된 상품끼리 서버가 계산한 순위·게이지를 허용한다. 이때 `rank_scope_verified_products_only` 사유를 한글로 바꾸고 목록 상단에 확인된 상품만의 순위임을 명시한다. 프런트엔드는 순위 범위를 전체 상품으로 확대하거나 자체적으로 순위·게이지를 다시 추정하지 않는다. 알려진 수량은 유지하고, 서버가 보류한 값은 그대로 둔다. 게이지가 제공될 때만 0~100 값을 표시하며 임의의 시험 점수로 바꾸지 않는다. 게시 검증, 확인 상품 범위의 순위 사용 가능 여부, 전체 상품 검증 완료를 따로 기록한다. 일부 상품의 순위·게이지와 범위 안내가 실제 화면에서 확인되면 그 범위의 사용 가능 상태만 기록하고, 남은 미확정 상품의 수량 근거와 첫 예약 실행은 별도 검증한다. 요약 저장이나 일부 순위 표시 성공만으로 전체 작업 완료를 선언하지 않는다.

취소·반품 신청 중인 수량은 완료 전 결제수량에 포함하고 `pending_claim_included_until_completed`를 한글로 안내한다. 완료된 취소·반품만 수량 증거가 주문 품목과 일치할 때 차감한다. 교환은 원품·대체품의 이전 관계와 완료 증거를 대조해 중복 계산을 막으며, 완료됐다는 이유만으로 판매수량에서 일괄 차감하지 않는다. 진행 중인 신청 수량을 미리 빼지 않으며 관계·완료 여부·수량이 불명확하면 해당 상품은 보류하고 0으로 간주하지 않는다.

요청수량이 `null`이면 0 또는 완료수량으로 치환하지 않는다. 완료 취소·반품은 정확한 상세의 품목·상품·상태·수량 증거를 직접 대조하며, 요청수량과 완료수량을 같은 값으로 간주하지 않는다. C40과 네이버 취소 요청 상태가 함께 남으면 코드 오류라고 단정하지 말고 독립적인 완료·환불 근거를 확인한다. 조건부 단일 품목 표본이 통과해도 전체 상품 집계에 반영됐다고 보고하지 않는다.

클레임 판정 재발 방지: `cancel_date`와 `return_confirmed_date`의 공존만으로 실패시키지 않는다. `return_confirmed_date`는 반품 승인 일시이므로 완료 증거로 단독 사용하지 않고 상태·상세·품목 주문·상품·수량·철회 증거의 일치를 확인한다. 수거 전 진행 상태인 `R30`은 완료 전 수량을 유지하되 부분 완료 증거와 모순되면 보류하며, `C00`+`naverCANCEL_REQUEST`·`R00`+`RETURN_REQUEST` 같은 호환 요청 상태를 일괄 보류하지 않는다. `E00`만으로 정상 확정하거나 대체 품목 주문이 없다는 이유로 원품을 일괄 보류하지 말고 전체 주문의 대체 품목·이전 관계·완료 증거를 검증한다. `R30→R40`, `E00→N01/E40` 전환에서 원품과 대체품을 중복 가산하지 않는다. 어댑터는 실제 단일 배열 응답과 묶음·증정의 모순 필드를 버리지 않고 보존하며, 이 입력 형식부터 상태 전환까지 통합 회귀 검증에 포함한다.

출시일·판매 가능한 재고·관찰기간이 부족하면 `pending`을 유지한다. 단순 꼴찌라는 이유만으로 부진을 붙이지 않는다. 영문 사유 코드는 한글 안내로 매핑하며 모르는 코드는 일반 한글 안내로 대체한다.

2026-10-07 이후 목록은 전체 판단 대신 확인된 판매량·기간 주문 반품률을 상시 표시한다. 최신 UI 규칙은 프로젝트 MD의 v101 절을 따른다. 기존 재고/출시 근거 부족은 원인·품질 평가에서 유지하며, 제품 접기를 디자이너의 읽기 경로로 다시 도입하지 않는다. 기록 버튼은 별도 창을 열고 초안·현재 표시 스냅샷을 보존한다.

최소 검증은 모바일 320px부터 데스크탑까지 넘침 여부, 검색·필터·정렬, 한글 사유, 미확인 수량, 권한 거절, 로그아웃 경합, 기본 앱 인증 콜백과 쓰기가 발생하지 않는 판매 로그인이다. 개선 기록은 펼친 제품의 `predReflection` 필드만 읽고 사진 전체를 다시 받지 않는다.

## 재사용·배포 상태 기록

프로젝트 루트에서 러너 검증은 `node --test tests/sync-sales.test.mjs tests/publish-sales.test.mjs`로 실행한다. 배포 HTML과 루트 `scripts/`, `tests/`, `.github/workflows/`가 저장소의 재사용 기준이다. `runner/` 접두사가 있는 경로를 가정하지 않는다. UI의 67개 fixture 검증과 인쇄 6개 검증은 원 작업 환경의 별도 검증 이력이며 로컬 테스트 파일과 Playwright 경로를 이 스킬의 필수 실행 경로로 요구하지 않는다. UI를 수정할 때는 현재 환경의 브라우저 도구로 위 화면·인증 조건을 확인한다.

러너는 28일 원천 수집량을 고려해 전체 처리 최대 120분, 상태 조회 최대 600회, GitHub 작업 최대 125분으로 제한한다. 서버의 `retryAfterSeconds`는 0~300 범위만 허용한다. 값이 이상하거나 제한을 넘으면 마지막 정상 집계를 유지하고 실패를 보고한다.

시작 요청 계약 수정 후 취소·반품 대조에서 `CLAIM_RECONCILIATION_REQUIRED`가 발생한 이력이 있다. 이 오류를 무시하고 0건·완료 집계로 게시하지 않는다. 수집기 수정과 배포, 실제 주문 대조를 확인한 다음 재실행한다.

완료 후 기획 MD와 JSON의 상태·검증 결과·남은 작업을 함께 갱신한다. 사용자가 요청한 GitHub 커밋과 버전 ZIP·Drive 전달은 실제 완료 여부를 각각 기록한다. 이 참조 파일 자체는 예약 집계 설치나 배포를 수행하지 않는다.
